# نیازمندی‌ها (Requirements)

> این سند پیش‌نویس است و به‌تدریج کامل می‌شود.

## ۱. شرح مسئله

پیدا کردن آگهی‌های خوب در دیوار به‌صورت دستی زمان‌بر است؛ آگهی‌های باارزش سریع فروش می‌روند. نیاز به ابزاری داریم که به‌صورت خودکار و پیوسته دیوار را پایش کند و موارد منطبق را فوراً اطلاع دهد.

## ۲. قابلیت‌های اصلی (MVP)

- [ ] تعریف «جستجوهای ذخیره‌شده»: پارامترهای جستجو (شهر/دسته/قیمت/کلمات کلیدی)
- [ ] فیلترها دقیقاً با کلیدهای بومی دیوار در کانفیگ — pass-through بدون ترجمه (`docs/configuration.md`)
- [ ] فیلتر جغرافیایی با allowlist محله‌ها از تنظیمات (تطبیق نرمال‌شده روی `district_persian` — ADR-0006) — فقط **گیت نوتیف** است: آگهی ردشده جزئیات/امتیاز/انبار کامل می‌گیرد ولی پیام نمی‌گیرد و ردیف delivery نمی‌سازد (اصلاح ۲۰۲۶-۰۹-۱۸)
- [ ] جدول نگاشت نام محله → district ID: برداشت خودکار از جزئیات هر آگهی + ویرایش دستی با CLI (`district`) — ADR-0006
- [ ] پایش دوره‌ای (polling) با بازه قابل تنظیم
- [ ] تشخیص آگهی جدید بر اساس token + watermark زمانی (عدم ارسال مجدد موارد قبلاً دیده‌شده)
- [ ] نرمال‌سازی پارامترهای ملک (ارقام فارسی، واحدها، قیمت توافقی، سال‌ساخت→عمر، آشتی قیمت‌متری — `docs/divar-api.md` بخش ۸)
- [ ] گرفتن جزئیات آگهی جدید از `posts-v2/web/{token}` (fallback HTML) برای **همهٔ آگهی‌های جدید** — allowlist فقط گیت نوتیف است (ADR-0009 — اصلاح ۲۰۲۶-۰۹-۱۸)؛ poll اول (baseline) هم پردازش کامل می‌گیرد: جزئیات + امتیاز + نوتیفِ ممتازها، فقط صفحهٔ اول (ADR-0007)
- [ ] خط لولهٔ دو مرحله‌ای poll: اول ذخیرهٔ همهٔ آگهی‌های جدید با جزئیات (`scoring_state: pending`)، بعد امتیازدهی دسته؛ آشتی‌سازی `pending`های معلق در startup (ADR-0001/0012)
- [ ] امتیازدهی قاعده‌محور روی فیلدهای search + جزئیات: قیمت، قیمت‌متری، متراژ، اتاق، عمر، طبقه، امکانات، محله، عنوان؛ نوتیف فقط برای امتیاز ≥ حداقل (`min_score`)
- [ ] درج امتیاز و شکست آن در پیام اطلاع‌رسانی
- [ ] ارسال اطلاع‌رسانی چندکاربره تلگرام با ثبت‌نام در بات: `/start` → پسورد مشترک → username یونیک → اتصال خودکار `chat_id` در دیتابیس؛ دستورات `/start` / `/resend YYYY/MM/DD` / `/help` / `/status` (ADR-0010؛ جزئیات: `configuration.md` بخش ۳.۱)
- [ ] مدل پخش عمومی (broadcast): همهٔ کاربران تلگرامِ ثبت‌شده و همهٔ گیرنده‌های ایمیل، همهٔ آگهی‌های ممتاز را می‌گیرند؛ جستجوها و امتیازدهی سراسری می‌مانند (ADR-0010)
- [ ] کانال ایمیل با چند گیرنده از کانفیگ (هر گیرنده یک تحویل مستقل؛ محتوای plain text با همان فیلدهای پیام تلگرام؛ Subject: «Top Divar — {عنوان} (امتیاز {N})»؛ تحویل = پذیرش SMTP — ADR-0010)
- [ ] جدول پیگیری ارسال (`delivery`): تحویل at-least-once — ردیف per (آگهی، کانال، گیرنده)، علامت `sent` فقط بعد از موفقیت + **سویپ retry دوره‌ای** `notify.retry_interval` (پیش‌فرض ۳۰m) با سقف `sweep_max_sends` (پیش‌فرض ۵۰ per channel/سویپ) و ستون‌های `attempts`/`last_error`/`last_attempt_at` (ADR-0010 اصلاح ۲۰۲۶-۰۹-۱۷)
- [ ] طبقه‌بندی سه‌دستهٔ خطاهای ارسال (اصلاح ۲۰۲۶-۰۹-۱۸): گذرا (سویپ بعدی) / قابل‌احیا (backoff ردیف‌محور `next_attempt_at` تا سقف ۲۴h) / ابدی (وضعیت **`dead`** — مثل 403/block تلگرام؛ دیگر ارسال نمی‌شود)
- [ ] جبران تعاملی (backfill): هر تعامل کاربر ثبت‌شده → ارسال فوری `pending`های او، قدیمی‌ترین اول، سقف ۷ روز — **مقدم بر backoff ردیف‌محور** (تعامل = ارسال بی‌تاب به `next_attempt_at`)؛ در کنار سویپ retry دوره‌ای (ADR-0010 — G5)
- [ ] ارسال مجدد از تاریخ (`/resend`، تاریخ شمسی): فقط به کاربر درخواست‌کننده؛ **«ممتاز» = وجود ردیف delivery برای آگهی** (بدون ستون جدید)؛ سقف ۳۰ روز؛ cooldown ‏۱۰ دقیقه per user (ADR-0010 — اصلاح ۲۰۲۶-۰۹-۱۸)
- [ ] مدیریت کاربر با CLI (اصلاح ۲۰۲۶-۰۹-۱۸): `user list` / `user remove <username>` — حذف کاربر، `pending`های او را هم `dead` می‌کند؛ شمارندهٔ سراسری تلاش ناموفق پسورد (~۲۰/۱۰m → هشدار اپراتور)؛ 409 تلگرام در getUpdates گذرا با backoff کوتاه
- [ ] هشدار اپراتور: systemd `Restart=always` + `WatchdogSec`/`sd_notify` (تسک heartbeat جدا از صف — ADR-0012) + `OnFailure` → پیام تلگرام از `.env: TELEGRAM_OPS_CHAT_ID`؛ و یک پیام throttleشده (حداکثر ۱ در ۲۴ ساعت) بعد از `max_consecutive_errors` متوالی دیوار (ADR-0003 — مصوب ۲۰۲۶-۰۹-۱۷)؛ غیبت `TELEGRAM_BOT_TOKEN`/`TELEGRAM_OPS_CHAT_ID` → هشدار startup فارغ از کانال فعال
- [ ] بکاپ SQLite با `VACUUM INTO` + systemd timer روزانه، ~۷ نسخهٔ چرخشی (ADR-0001 — اصلاح ۲۰۲۶-۰۹-۱۸)
- [ ] بارگذاری مجدد کانفیگ در startup و SIGHUP (`systemctl reload`)؛ YAML نامعتبر در reload → کانفیگ قبلی + ERROR (ADR-0011)
- [ ] محتوای پیام: عنوان — برچسب جستجو، فیلدهای ملک، امتیاز و شکست فشردهٔ آن، لینک مستقیم — قالب مصوب: `docs/configuration.md` بخش ۳
- [ ] ذخیره تاریخچه آگهی‌های دیده‌شده (شامل موارد زیر آستانه، برای کالیبراسیون)

## ۳. قابلیت‌های آتی (Backlog)

- [ ] معیار کمیابی نسبی: قیمت‌متری در برابر میانهٔ همتای غلتان (نه دلار، نه میانگین سراسری) + **بازارزیابی دوره‌ای همهٔ املاک با رشد همتا** (نوتیف فقط در گذار «هرگز ممتاز نبوده → ممتاز»؛ گذار تأخیری > ۷ روز فقط امتیاز) — طراحی: `docs/deal-scoring.md` (بخش ۴.۶)، ADR-0008؛ پیش‌نیاز `size`/`price_per_square` از جزئیات تأمین شده؛ داده از `raw_json` ذخیره‌شده
- [ ] فیلترهای هوشمند (کلمات ممنوعه، حذف آگهی‌های تجاری/اسپم — قاعده قطعی `is_dealer`)
- [ ] کانال Ntfy (interface دامنهٔ `Notifier` برای آینده باز می‌ماند — ADR-0002)
- [ ] مدیریت جستجو از داخل تلگرام (Bot Gateway کامل: افزودن/حذف جستجو، تغییر بازه — دامنهٔ MVP فقط ثبت‌نام/جبران/ارسال‌مجدد است، ADR-0010)
- [ ] هضم/پیام خلاصهٔ «دادهٔ ناقص» به کاربر اگر دادهٔ ناقص (مثل سال ساخت غایب) به آستانهٔ بحرانی رسید (`deal-scoring.md` بخش ۴.۲ و ۱۲)
- [ ] نوتیف «کاهش قیمت» بر پایهٔ لاگ رویداد تغییر قیمت (`deal-scoring.md` بخش ۴.۴ و ۱۲)

## ۴. محدودیت‌ها و ملاحظات

- **نرخ درخواست:** فاصله منطقی بین درخواست‌ها برای جلوگیری از مسدود شدن
- **قابلیت اطمینان:** تحمل خطای شبکه و تغییر ساختار صفحات/API دیوار
- **امنیت:** توکن بات تلگرام، پسورد ثبت‌نام بات، رمز SMTP و chat_id اپراتور (`TELEGRAM_OPS_CHAT_ID`) فقط از `.env`
- **زبان رابط کاربری:** فارسی
- **تورم و قیمت مسکن:** آستانهٔ ثابت تومانی فقط سقف بودجه است؛ تشخیص «آگهی خاص» با مقایسهٔ نسبی همتا انجام می‌شود (`docs/deal-scoring.md`)

## ۵. سناریوهای استفاده

1. کاربر جستجوی «آپارتمان ۸۰ متری در منطقه X زیر Y تومان» را ذخیره می‌کند.
2. سیستم هر N دقیقه نتایج را بررسی می‌کند.
3. آگهی جدیدِ منطبق → امتیازدهی؛ در صورت عبور از حداقل امتیاز، پیام تلگرام با لینک مستقیم و امتیاز.
