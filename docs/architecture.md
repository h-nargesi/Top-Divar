# معماری (Architecture)

> این سند پیش‌نویس است؛ تصمیم‌های نهایی اینجا ثبت می‌شوند.

## تقسیم‌بندی معماری

معماری از نوع Ports & Adapters (شش‌ضلعیِ سبک) است: همه وابستگی‌ها به لایه دامنه است و هیچ جزئی به پیاده‌سازی مشخص Fetcher/Storage/Notifier وابسته نیست — تا هر جزء بدون تغییر بقیه قابل تعویض باشد.

### ۱. دامنه و قراردادها (Domain & Ports)

مدل‌های داده و interfaceهای سیستم. مرجع مشترک همه بخش‌ها؛ به هیچ بخش دیگری وابسته نیست.

- موجودیت‌ها: `Search`, `Ad`, `AdEvent`
- قراردادها: `Fetcher`, `AdRepository`, `Notifier`

### ۲. خط لوله اصلی (Core Pipeline)

منطق کسب‌وکار؛ فقط با قراردادهای دامنه کار می‌کند.

- **Scheduler** — حلقه پایش؛ اجرای هر جستجو با بازه خودش، رعایت نرخ درخواست کلی
- **Detector** — مقایسه نتایج تازه با تاریخچه (diff بر اساس `divar_token` و watermark `sort_date`)، تشخیص جدید/bump — semantics کامل: `docs/divar-api.md` بخش ۹ (مرز watermark، poll اول، سقف صفحات، آگهی مشترک بین جستجوها)
- **Normalizer** — تبدیل کارت search + ویجت‌های جزئیات به فیلدهای نرمال‌شده (ارقام فارسی، سال ساخت→عمر، آشتی قیمت، طبقه، اتاق، امکانات) — مرجع: `docs/divar-api.md` بخش ۷ و ۸
- **Scorer** — اعمال قواعد امتیازدهی کانفیگ (`docs/configuration.md` بخش ۲) روی فیلدهای نرمال‌شده؛ خروجی: امتیاز + شکست آن؛ شرط نوتیف: `score >= min_score`. قواعد نسبی کمیابی (همتای غلتان) در فاز بعد: `docs/deal-scoring.md`، ADR-0008

### ۳. آداپتورها (Adapters)

پیاده‌سازی قراردادها برای دنیای بیرون.

- **DivarFetcher** — `search()` روی `postlist/w/search` و `get_post(token)` روی `posts-v2/web/{token}` (fallback HTML) — تحلیل: `docs/divar-api.md`، نمونه‌ها: `docs/fetch-sample.md`
- **SqliteRepository** — تاریخچه آگهی‌ها، جستجوها، تنظیمات (WAL، ایندکس یونیک روی `divar_token`)
- **TelegramNotifier** / **EmailNotifier** — کانال‌های MVP؛ مستقل و بدون زنجیرهٔ fallback (ADR-0002). **NtfyNotifier** → backlog (ADR-0002)

### ۴. مقاطع مشترک و ورودی (Cross-cutting & Entry)

- **Config** — بارگذاری `.env` و فایل تنظیمات؛ اعتبارسنجی مقادیر
- **Logging** — لاگ ساختاریافته از وضعیت پایش و خطاها
- **CLI** — نقطه ورود: اجرای سرویس (`run`)، اعتبارسنجی کانفیگ (`validate`)، مدیریت نگاشت محله‌ها (`district list|add|remove` — ADR-0006)، مدیریت کاربر (`user list | user remove <username>` — ADR-0010/0011) و `reset-watermark <search_id>` (baseline عمدی، اختیاری) — مدیریت جستجوها با ویرایش `config.yaml` انجام می‌شود (ADR-0011)
- **Bot Gateway** (MVP — ADR-0010) — long-polling `getUpdates` تلگرام با دامنهٔ مینیمال: ثبت‌نام (`/start` → پسورد مشترک → username یونیک)، جبران `pending`ها در هر تعامل، ارسال‌مجدد از تاریخ؛ دستورات: `/start` / `/resend YYYY/MM/DD` / `/help` / `/status` (جزئیات: `configuration.md` بخش ۳.۱)؛ مدیریت جستجو از بات → backlog. نکته: `getUpdates` یعنی فقط یک نمونهٔ فعال از سرویس

## جریان داده

1. Scheduler سر رسید جستجوی بعدی را می‌گیرد → Fetcher.`search()` (`postlist/w/search` با `sort` جدیدترین)
2. Detector نتیجه را با تاریخچه در Storage مقایسه می‌کند (watermark روی `sort_date`)
3. **مرحلهٔ ذخیره (تصمیم ۱۹ — اصلاح ۲۰۲۶-۰۹-۱۸):** همهٔ آگهی‌های جدیدِ poll — فارغ از allowlist جغرافیا — جزئیات می‌گیرند (`get_post(token)` با فاصلهٔ `detail_min_interval`) و با فیلدهای نرمال‌شده و `scoring_state: pending` ذخیره می‌شوند؛ allowlist فقط «گیت نوتیف» است، نه گیت پردازش (ADR-0006/0009)
4. **مرحلهٔ امتیازدهی دسته:** پس از پایان مرحلهٔ ذخیره، آگهی‌های `scoring_state: pending` امتیازدهی می‌شوند (Normalizer → Scorer) و `scoring_state: scored` می‌گیرند؛ در startup آگهی‌های معلق در `scoring_state: pending` (باقی‌مانده از کرش/ری‌استارت) همین‌جا آشتی و امتیازدهی می‌شوند
5. امتیاز `>= min_score` **و** عبور از گیت allowlist → تراکنش واحد در Storage: ردیف‌های `delivery` به‌ازای هر (آگهی، کانال، گیرنده) با وضعیت `pending` — **قبل از** ارسال (ADR-0010؛ پیام شامل امتیاز و شکست آن)؛ آگهی ردشده توسط allowlist برای هیچ کانالی (حتی ایمیل) ردیف delivery نمی‌گیرد (G6/ADR-0006)
6. ارسال مستقل به‌ازای هر کانال/گیرنده (بدون زنجیرهٔ «کانال بعدی»): موفق → علامت `sent`؛ خطای گذرا → ردیف `pending` می‌ماند (تا سویپ بعدی)؛ خطای قابل‌احیا → `pending` + `next_attempt_at` با backoff؛ خطای ابدی → `dead` (ADR-0010)
7. poll اول = baseline با پردازش کامل (جزئیات + امتیاز + نوتیف اگر ممتاز — ADR-0007) و فقط صفحهٔ اول؛ bump = گرفتن دوبارهٔ جزئیات، نوتیف فقط با `notify_on_bump`

## تصمیم‌های ثبت‌شده (ADRها)

### ADR-0001: Storage = SQLite

- تک‌اپراتور با چندگیرندهٔ کم‌تعداد — پخش عمومی (ADR-0010) — و حجم کم → بدون سرور، وابستگی صفر در Python
- **بکاپ (اصلاح ۲۰۲۶-۰۹-۱۸):** `VACUUM INTO` (اسنپ‌شات سازگار، بدون توقف سرویس) + systemd timer روزانه؛ نگه‌داشت ~۷ نسخهٔ روزانه (چرخشی) در `data/backups/` — جایگزین روش پیشینِ کپیِ مستقیم فایل دیتابیس که با WAL ناسازگار/ناامن بود
- `PRAGMA journal_mode=WAL` و `busy_timeout`
- ایندکس یونیک روی `divar_token` (کلید تشخیص تکراری در Detector)
- ذخیره `raw_json` آگهی برای تحلیل‌های آینده (معیار کمیابی نسبی — ADR-0008، `docs/deal-scoring.md`)
- فایل دیتابیس در `data/` و gitignored؛ سیاست purge (مصوب ۲۰۲۶-۰۹-۱۷؛ اصلاح همان روز جلسهٔ دوم — تصمیم «۳۰ روز ثابت» → مشتق‌شده): حذف ردیف کامل آگهی‌های قدیمی‌تر از `window_days_max + purge_margin_days` (پیش‌فرض ۳۰+۷=۳۷، مشتق‌شده؛ `window_days_max` پیش‌فرض سامانه‌ای ۳۰ دارد، حتی وقتی بلوک `relative` غایب/غیرفعال است)؛ purge نباید کوتاه‌تر از `window_days_max` شود
- **tombstone ماندگار برای همیشه (تصریح ۲۰۲۶-۰۹-۱۸):** ردیف کامل آگهی purge می‌شود ولی tombstone مینیمال (token + آخرین `sort_date` دیده‌شده) **هرگز حذف نمی‌شود** — نردبان/بازنشرِ هر چند سال بعد هم دوباره «جدید» تلقی نمی‌شود؛ حجم tombstone ناچیز است و پاک‌کردنش کم‌فایده
- جدول `district_id_map` — نگاشت نام محله → district ID (ADR-0006): یونیک روی `(city_id, district_id)` و `(city_id, district_name_normalized)`؛ تقدم `manual` > `auto`
- جدول `users` (ADR-0010) — ثبت‌نام در بات تلگرام: `username` یونیک + نگاشت به `chat_id`
- جدول `delivery` (ADR-0010) — یک ردیف به‌ازای هر (آگهی، کانال، گیرنده) با وضعیت `pending | sent | dead` (اصلاح ۲۰۲۶-۰۹-۱۸: افزودن `dead`)؛ ستون‌های ردگیری خطا: `attempts`، `last_error` (متن بریده به ~۵۰۰ کاراکتر)، `last_attempt_at` (مصوب ۲۰۲۶-۰۹-۱۷) + `next_attempt_at` (backoff ردیف‌محور — اصلاح ۲۰۲۶-۰۹-۱۸)؛ ردیف‌های هر آگهی همراه همان آگهی purge می‌شوند (`window_days_max + purge_margin_days` — پیش‌فرض ۳۰+۷=۳۷)؛ سازگار با جبران ۷روزه و سقف ۳۰روزهٔ ارسال‌مجدد (هر دو ≤ ۳۷)
- **ستون `scoring_state` روی آگهی (اصلاح ۲۰۲۶-۰۹-۱۸ — تصمیم ۱۹):** `pending | scored`؛ خط لولهٔ دو مرحله‌ای poll (اول ذخیره با جزئیات، بعد امتیازدهی دسته) و آشتی‌سازی startup متکی به همین ستون است («جریان داده»)
- PostgreSQL فقط در صورت چندمیزبانی/سرویس‌دادن به اپراتورهای متعدد در آینده (چندگیرندهٔ پخش عمومی دلیل تغییر DB نیست)

### ADR-0002: اطلاع‌رسانی چندکاناله — Telegram + Email در MVP

- کانال‌های MVP: **Telegram** (Bot API مستقیم — `POST api.telegram.org/bot<TOKEN>/sendMessage` با `chat_id`, `text`, `parse_mode=HTML`, `disable_web_page_preview: true`؛ خطاهای معتبر: 429 / 403 / 400 — رفتار 429: انتظار `retry_after` با سقف ۶۰ ثانیه + یک تلاش مجدد همان پیام، تکرار → دستهٔ قابل‌احیا با `next_attempt_at` (طبقه‌بندی خطا — ADR-0010 اصلاح ۲۰۲۶-۰۹-۱۸)؛ مصوب ۲۰۲۶-۰۹-۱۷) و **Email** (SMTP)؛ هر دو از interface دامنهٔ `Notifier` پیاده می‌شوند
- **Ntfy صریحاً backlog است** — در MVP ساخته نمی‌شود؛ interface `Notifier` برای افزودن آیندهٔ آن باز می‌ماند
- کانال‌ها **مستقل**اند: زنجیرهٔ «کانال بعدی/fallback» حذف شد؛ خطای هر کانال فقط برای همان کانال لاگ می‌شود و مانع ارسال بقیه نمی‌شود (تحویل at-least-once و جبران: ADR-0010)
- **دامنهٔ `HTTPS_PROXY` (اصلاح ۲۰۲۶-۰۹-۱۸):** اگر در `.env` بود، **همهٔ فراخوانی‌های Bot API تلگرام** از آن استفاده می‌کنند — نه فقط `TelegramNotifier`: شامل Bot Gateway (`getUpdates`/`sendMessage` ثبت‌نام و دستورات) و پیام `curl`ی `OnFailure` یونیت systemd (ADR-0003)؛ بدون شرط جغرافیایی. با استقرار داخل ایران (ADR-0003) پروکسی شرط دسترسی به تلگرام است — پذیرش ریسک: خرابی پروکسی = قطع نوتیف/هشدار؛ پایش دیوار و pendingها ادامه دارند
- **SMTP (اصلاح ۲۰۲۶-۰۹-۱۸):** اعتبارسنجی گواهی TLS الزامی است (`encryption: none` فقط آزمایش محلی + هشدار — `configuration.md` بخش ۳.۴)؛ نکتهٔ استقرار داخل ایران: بعضی پرووایدرهای ایمیل خارجی IPهای ایران را بلاک می‌کنند — انتخاب پرووایدر SMTP باید در عملیات استقرار لحاظ شود
- **HTML ایمن (مصوب ۲۰۲۶-۰۹-۱۷):** همهٔ متن‌های متغیر پیام (عنوان آگهی، محله، شهر، برچسب جستجو، شکست امتیاز و…) قبل از درج در قالب escape استاندارد می‌شوند (`&`→`&amp;`، `<`→`&lt;`، `>`→`&gt;`)؛ تگ‌های HTML فقط در اختیار قالب خود پیام‌اند — وگرنه یک عنوان حاوی `<` پیام را با خطای 400 تلگرام می‌اندازد

### ADR-0003: سرویس همیشه‌روشن، نه اکستنشن مرورگر

- پایش پیوسته ۲۴/۷، SQLite و SMTP و دستورات بات همگی به یک پروسه همیشه‌روشن نیاز دارند؛ اکستنشن (MV3) این را تضمین نمی‌کند
- استقرار (مصوب ۲۰۲۶-۰۹-۱۷؛ **اصلاح ۲۰۲۶-۰۹-۱۸ — داخل ایران**): **systemd روی VPS داخل ایران** — نزدیکی به دیوار (تأخیر/پایداری بهتر، حذف ریسک ژئو/IP خارجی برای API غیررسمی دیوار)؛ دسترسی به تلگرام از طریق `HTTPS_PROXY` روی همهٔ فراخوانی‌های Bot API (ADR-0002)؛ Docker رد شد (لایهٔ اضافه برای تک‌سرویسِ تک‌نمونه؛ فقط اگر چندسرویسی شد برمی‌گردد)؛ cron با مدل همیشه‌روشن ناسازگار است؛ سرور خانگی همچنان فقط با `HTTPS_PROXY` (ADR-0002) ممکن می‌ماند
- **پذیرش ریسک پروکسی (اصلاح ۲۰۲۶-۰۹-۱۸):** با استقرار داخل ایران، پروکسی تلگرام گلوگاه است — خرابی پروکسی = قطع نوتیف/هشدار اپراتور؛ پایش دیوار، ذخیره و ردیف‌های `pending` ادامه دارند و بعد از بازگشت پروکسی سویپ/جبران ارسال می‌کنند (ADR-0010)
- پایداری و هشدار اپراتور (مصوب ۲۰۲۶-۰۹-۱۷): `Restart=always` (کرش → راه‌اندازی مجدد)؛ `WatchdogSec=300` + `sd_notify` از داخل برنامه (تشخیص قفل‌شدن حلقهٔ اصلی و ری‌استارت — تسک heartbeat جدا از صف کاری، ADR-0012)؛ یونیت `OnFailure=` → یک پیام تلگرام با `curl` به Bot API از `.env: TELEGRAM_OPS_CHAT_ID` (از طریق همان `HTTPS_PROXY` — ADR-0002)؛ بعد از `max_consecutive_errors` متوالی دیوار → یک پیام هشدار با throttle حداکثر ۱ در ۲۴ ساعت (به همان chat اپراتور)
- اکستنشن حداکثر در آینده به‌عنوان **Fetcher مکمل** (خواندن DOM وقتی کاربر در دیوار است) → ثبت در backlog

### ADR-0004: منبع داده = API غیررسمی وب دیوار (v8) با فیلترهای pass-through

- پایش: `postlist/w/search` (ترتیب جدیدترین + صفحه‌بندی)؛ جزئیات: `posts-v2/web/{token}` (ADR-0009)؛ `mapview/viewport` رد شد (ADR-0006)؛ جغرافیا با **allowlist محله‌ها** روی `district_persian` (ADR-0006) — تحلیل: `docs/divar-api.md`
- بدنه درخواستِ فیلترها **عیناً از کانفیگ** ساخته می‌شود (`form_data` بدون ترجمه؛ `docs/configuration.md`) → فیلتر جدید دیوار بدون تغییر کد پشتیبانی می‌شود
- بدون احراز هویت در جستجو و جزئیات (فرض اولیه؛ بدون کوکی تأیید شد)، هدرهای مرورگر واقعی، نسخه `v8` پین
- تشخیص جدید بودن: `divar_token` + watermark `sort_date` (اولین صفحه با ترتیب جدیدترین)
- ریسک API خصوصی/متغیر → تنها از طریق `DivarFetcher` (ایزوله)، تست snapshot روی نمونه‌های `fetch-sample.md`
- **پذیرش ریسک ToS (اصلاح ۲۰۲۶-۰۹-۱۸):** استفاده شخصی، نرخ پایین (فاصله‌های `polling`، بدون درخواست موازی) و غیرتجاری؛ ریسک مسدودسازی/تغییر API پذیرفته شده و در صورت سرویس‌شدن عمومی، این تصمیم بازبینی می‌شود
- پارس DOM/CSS صفحه آگهی رد شد؛ JSON ویجت (و در fallback، همان JSON داخل `__PRELOADED_STATE__`) استفاده می‌شود — نه scraping جدول HTML

### ADR-0005: امتیازدهی قاعده‌محور با آستانه نوتیف

- موتور امتیازدهی جدا از فیلترهای جستجو: فیلتر = رد موارد بی‌ربط در سمت دیوار؛ امتیاز = سنجش «خوب بودن» در سمت ما
- قواعد در کانفیگ: `{field, op, value, points}` + قواعد پله‌ای (tiers) + امتیاز منفی (جریمه) — `docs/configuration.md` بخش ۲
- ورودی: فیلدهای نرمال‌شده از کارت search **و** جزئیات آگهی (ADR-0007 + ADR-0009)؛ فیلد غایب → `skip` قاعده (`on_missing_field` فقط `skip` است — مقدار `zero` حذف شد، اصلاح ۲۰۲۶-۰۹-۱۸)؛ تمایز «غایب» و «null صریح (توافقی)»: `configuration.md` بخش ۲
- شرط نوتیف: `score >= min_score`؛ پیام شامل امتیاز و شکست آن (برای کالیبراسیون قواعد)
- قواعد نسبی کمیابی → فاز بعد با معیار **میانهٔ همتای غلتان** (نه دلار، نه میانگین سراسری) — ADR-0008 و `docs/deal-scoring.md`؛ ذخیره `raw_json` (ADR-0001) آن را ممکن می‌کند

### ADR-0006: جغرافیا = allowlist محله‌ها روی `district_persian` (سمت کلاینت)

- مکانیزم جغرافیایی اصلی: کاربر در کانفیگ هر جستجو لیست محله‌های دلخواه (`districts`) را می‌دهد؛ پس‌فیلتر روی `district_persian` پاسخ `search` اعمال می‌شود (`docs/configuration.md` بخش ۱)
- **allowlist = گیت نوتیف فقط (اصلاح ۲۰۲۶-۰۹-۱۸):** آگهی خارج از لیست (یا بدون محله وقتی `allow_unknown_district: false`) **جزئیات، امتیاز و انبار کامل می‌گیرد** (شهروند کامل همتا/تاریخچه — `deal-scoring.md` بخش ۴.۲) و فقط **پیام** نمی‌گیرد؛ رفتار پیشینِ «ثبتِ seen بدون هیچ پردازشی» حذف شد. گیت بر «شایستگی نوتیف» اعمال می‌شود، نه فقط کانال تلگرام: آگهی ردشده **برای هیچ کانالی — حتی ایمیل — ردیف delivery نمی‌گیرد** (G6)
- `viewport` (پین‌های نقشه) رد شد: مختصاتش تقریبی است و مصرف‌کننده‌ای ندارد؛ اگر بعداً قاعده امتیاز جغرافیایی خواست شد برمی‌گردد
- استفاده از `bbox` رد شد (تصمیم 2026-09-17؛ پیش‌تر پیش‌فیلتر اختیاری سرور بود — مستطیل، محله‌های مجاور را هم می‌گرفت)؛ جغرافیا فقط از طریق allowlist محله‌ها
- تطبیق: **contains** روی متن نرمال‌شده (ي/ك عربی → فارسی، نیم‌فاصله → فاصله) — چون دیوار «نارمک» و «نارمک جنوبی» را جدا برمی‌گرداند
- **جدول نگاشت نام محله → district ID (خودکار + دستی — مصوب 2026-09-17):** دیوار فیلتر بومی `districts` (ID عددی محله) دارد. نگاشت در SQLite (`district_id_map` — ADR-0001) دو منبع دارد: (۱) **خودکار** — هر `get_post` موفق از `seo.bread_crumb` آیتمی را می‌گیرد که `name == seo.web_info.district_persian` و `districts` آن تک‌عضوی است (`slug_en` از `webengage.district`، `city_id` از `city.city_id`؛ نمونهٔ `gammaxvi`: «هروی» → `1024`)؛ ابهام → فقط لاگ؛ (۲) **دستی** — دستور CLI `district list|add|remove`. تقدم `manual` > `auto`. در ساخت بدنهٔ درخواست، نام‌های `districts` کانفیگ که نگاشت دارند به `form_data.districts` تزریق (merge) می‌شوند؛ نام‌های بی‌نگاشت با پس‌فیلتر `district_persian` می‌مانند — کانفیگ نام‌محور بدون شکست تغییر نمی‌کند (جزئیات برداشت: `divar-api.md` بخش ۱۲.۵)

### ADR-0007: استخراج لیست از کارت `search` — فیلدهای viewport از نگاشت حذف شد

- جدول نگاشت فیلدها (`divar-api.md` بخش ۷) پیش از این به `subtitle1/2` و `chips` از پاسخ `viewport` ارجاع می‌داد؛ پس از رد viewport (ADR-0006) آن ارجاع‌ها ناسازگار بودند → نگاشت لیست صرفاً بر اسکلت تأییدشده `POST_ROW` سوار شد
- فیلدهای لیست: `price` (نمایشی)، `district`، `city`، `title`، `is_promoted`، `sort_date`، `token`، `image_count`؛ `rebuilt` فقط بافت جستجو
- فیلدهای ملک (`price_per_square` / `size` / `rooms` / `construction_year` / امکانات / `floor`) از جزئیات می‌آیند (ADR-0009؛ `divar-api.md` بخش ۷.۴)
- semantics «فیلد غایب» در برابر «null صریح (توافقی)» تعریف شد (`configuration.md` بخش ۲) — جریمه توافقی اکنون قابل اجراست
- تشخیص جدید: token یونیک **سراسری** = مرجع dedup (حتی بین جستجوها)؛ watermark فقط سقف صفحه‌بندی (مرز `<`، آیتم‌های هم‌زمان پردازش می‌شوند)؛ poll اول = baseline با پردازش کامل (جزئیات + امتیاز + نوتیف اگر ممتاز) و فقط صفحهٔ اول (اصلاح ۲۰۲۶-۰۹-۱۸)؛ bump فقط با `notify_on_bump` (جزئیات: `divar-api.md` بخش ۹)

### ADR-0008: کمیابی = ارزانی نسبی در همتای غلتان (نه دلار، نه میانگین سراسری)

مرجع تفصیلی: [`docs/deal-scoring.md`](deal-scoring.md)

- مسئله: تورم آستانهٔ ثابت تومانی را می‌سوزاند؛ «آگهی خاص» یعنی نسبت قیمت به شرایط ملک در بازار **همین حالا** کمیاب باشد
- معیار اصلی: **قیمت هر متر** نسبت به **میانه** (و صدک / MAD) آگهی‌های همتا در پنجرهٔ ۱۴–۳۰ روز اخیر — نه میانگین همهٔ آگهی‌ها، نه تبدیل به دلار
- همتا تنگ است (شهر، محله، باند متراژ، باند سن نسبی ±۱۰ سال) با عقب‌نشینی پله‌ای و کف حجم نمونه (`min_cohort_size`؛ مصوب ۳۰)؛ امکانات قید همتا نیستند و اثرشان از طریق «متراژ مؤثر» در واحد مقایسه (`pps_eff`) می‌آید (مصوب ۲۰۲۶-۰۹-۱۷ جلسهٔ دوم — `deal-scoring.md` بخش ۴.۱)
- سقف بودجهٔ کاربر فیلتر سخت می‌ماند (قواعد مطلق MVP)؛ امتیاز کمیابی جداست و با بازار جلو می‌رود
- دلار ملاک کمیابی نیست و نمایش دلاری در پیام ساخته نمی‌شود (مصوب ۲۰۲۶-۰۹-۱۷ — `deal-scoring.md` بخش ۳.۱)؛ دلار حداکثر سقف بودجهٔ ذهنی کاربر است
- پیش‌نیاز داده: `size` / `price_per_square` از جزئیات آگهی (ADR-0009، `divar-api.md` بخش ۷.۴ و ۸.۶)؛ خودِ قواعد نسبی همچنان فاز بعد است
- کیفیت ملک با همتاسازی + جریمه‌های قاعده‌محور کنترل می‌شود؛ مدل پیش‌بینی قیمت فاز بعدی اختیاری است

### ADR-0009: جزئیات آگهی = `posts-v2/web/{token}` با fallback HTML

- کارت `search` برای فیلدهای کاربر (متراژ، سال ساخت، اتاق، قیمت‌متری، طبقه، پارکینگ/آسانسور/انباری) کافی نیست — تأییدشده با نمونه دوصفحه‌ای `POST_ROW`
- منبع عملیاتی: `GET https://api.divar.ir/v8/posts-v2/web/{token}` (JSON ویجت‌های `LIST_DATA`)؛ بدون کوکی تأیید شد
- fallback: صفحه `GET https://divar.ir/v/{token}` و خواندن `__PRELOADED_STATE__.currentPost.post` — همان ویجت‌ها با غلاف `dto` (نمونه `gap5-Twe` در `fetch-sample.md`)
- پارسر یک‌بار روی `{widget_type, data}` نوشته می‌شود و **هر دو شکل** JSON آرایه‌ای و SSR کلیددار را می‌پذیرد؛ پارس CSS/DOM ممنوع است
- API رسمی کنار (کلید `GET_POST`) در MVP نیست
- زمان گرفتن جزئیات (اصلاح ۲۰۲۶-۰۹-۱۸ — G1): برای **همهٔ آگهی‌های جدیدِ جستجو** فارغ از allowlist (allowlist فقط گیت نوتیف است — ADR-0006)؛ baseline هم با جزئیات است (ADR-0007) ولی poll اول همچنان فقط صفحهٔ اول را می‌پوشاند؛ bump دوباره می‌گیرد؛ آگهی مشترک بین جستجوها تکراری نمی‌گیرد
- عمر بنا از جزئیات نمی‌آید: `building_age = سال_شمسی_جاری − construction_year` (`divar-api.md` بخش ۸.۴)
- قیمت: متن «قیمت کل» و «قیمت هر متر» منبع‌اند؛ `webengage.price` ضرب تقریبی است و وقتی متن هست نادیده گرفته می‌شود؛ آشتی سه‌تایی با متراژ: بخش ۸.۶

### ADR-0010: تحویل at-least-once با جدول delivery و جبران تعاملی

> **اصلاح ۲۰۲۶-۰۹-۱۷ (نشست بستن ابهام‌ها):** «بدون retry خودکار» لغو شد و جای خود را به **سویپ retry دوره‌ای** داد؛ **اصلاح ۲۰۲۶-۰۹-۱۸:** خطاها سه دسته می‌شوند (گذرا/قابل‌احیا/ابدی)، وضعیت `dead` و backoff ردیف‌محور (`next_attempt_at`) اضافه می‌شود، سویپ سقف ارسال می‌گیرد و تعریف «ممتاز» در `/resend` عوض می‌شود؛ بقیهٔ تصمیم‌ها پابرجا هستند.

- مدل گیرنده‌ها **پخش عمومی (broadcast)** است: همهٔ کاربران تلگرامِ ثبت‌شده و همهٔ گیرنده‌های ایمیلِ کانفیگ، همهٔ آگهی‌های ممتاز را می‌گیرند؛ جستجوها و امتیازدهی سراسری/کانفیگی می‌مانند — فیلتر per-user وجود ندارد
- جدول `delivery`: یک ردیف به‌ازای هر (آگهی، کانال، گیرنده) با وضعیت `pending | sent | dead` (اصلاح ۲۰۲۶-۰۹-۱۸: افزودن `dead`)
- تراکنش واحد: ذخیرهٔ آگهی + همهٔ ردیف‌های delivery **قبل از** ارسال؛ علامت `sent` فقط **بعد از** موفقیت ارسال → تحویل at-least-once (تکرار نادر در اثر کرشِ بینِ ارسال و علامت‌گذاری پذیرفته است)
- **طبقه‌بندی سه‌دستهٔ خطاهای ارسال (اصلاح ۲۰۲۶-۰۹-۱۸):**

  | دسته | رفتار | نمونه‌ها |
  |---|---|---|
  | **گذرا (transient)** | ردیف `pending` می‌ماند؛ تلاش در سویپ بعدی (بدون backoff ردیف‌محور) | خطای شبکه/قطع موقت، 5xx، 429 تلگرام پس از تلاش مجدد همان پیام، 409 تلگرام در `getUpdates` |
  | **قابل‌احیا (resurrectable)** | `pending` + `next_attempt_at` با backoff نمایی تا سقف ۲۴ ساعت؛ جرقهٔ دوباره با موفقیت، ردیف را به چرخهٔ عادی برمی‌گرداند | 429 تلگرام (پس از تلاش مجدد)، انقضای موقت SMTP، `retry_after` بلند |
  | **ابدی (eternal)** | وضعیت `dead` — دیگر ارسال نمی‌شود؛ لاگ + شمارنده برای اپراتور | 403/block تلگرام، 400 تلگرام (پارامتر بد)، رد شدن دائم SMTP، گیرندهٔ ایمیل نامعتبر |

  خطاها دیگر «همه گذرا» فرض نمی‌شوند؛ طبقه‌بندی بر اساس نوع خطا در آداپتور هر کانال مشخص می‌شود و خطای ناشناخته گذرا در نظر گرفته می‌شود (محافظه‌کارانه).
- **سویپ retry دوره‌ای (اصلاح ۲۰۲۶-۰۹-۱۷؛ تکمیل ۲۰۲۶-۰۹-۱۸):** سرویس در بازهٔ `notify.retry_interval` (پیش‌فرض ۳۰ دقیقه) ردیف‌های `pending` را قدیمی‌ترین اول ارسال می‌کند (تلگرام با فاصلهٔ ~۱ ثانیه، ایمیل با فاصلهٔ ~۲ ثانیه) با **سقف `sweep_max_sends`** (پیش‌فرض ۵۰ پیام per channel در هر سویپ — مازاد به سویپ بعدی می‌رود)؛ ردیف‌های `next_attempt_at` در آینده فقط بعد از سر رسیدش ارسال می‌شوند؛ ردگیری با ستون‌های `attempts` / `last_error` / `last_attempt_at` / `next_attempt_at` (ADR-0001) + لاگ
- **جبران (backfill):** هر update دریافتی از کاربرِ ثبت‌شده (هر پیام، از جمله `/start` تکراری) → ارسال همهٔ `pending`های او، قدیمی‌ترین اول، سقف `backfill_days: 7`؛ **جبران تعاملی backoff ردیف‌محور را override می‌کند (G5):** تعامل کاربر = ارسال فوری pendingهای او بی‌تاب به `next_attempt_at` (ردیف‌های `dead` را برنمی‌گرداند)؛ در کنار سویپ دوره‌ای می‌ماند — یعنی ارسال فوری به‌جای انتظار تا سویپ بعدی
- **ارسال مجدد از تاریخ (`/resend YYYY/MM/DD` — تکمیل ۲۰۲۶-۰۹-۱۷؛ اصلاح ۲۰۲۶-۰۹-۱۸):** کاربر تاریخ شمسی می‌دهد → همهٔ ممتازهای از آن تاریخ (حتی قبلاً ارسال‌شده) **فقط به همین کاربر** دوباره ارسال می‌شوند (ایمیل و بقیهٔ کاربران نمی‌گیرند)؛ **«ممتاز» = وجود ردیف delivery برای آن آگهی** (بدون ستون جدید — تصمیم ۱۳): آگهی‌ای که گیت allowlist یا `min_score` را نگذرانده، ردیفی ندارد و `/resend` هم نمی‌شود؛ سقف ۳۰ روز (≤ حد purge = ۳۷ روز)؛ مستقل از جدول delivery (وضعیت ردیف‌های قبلی را تغییر نمی‌دهد)؛ **cooldown ‏۱۰ دقیقه** per user برای دستور (state در حافظه؛ درخواست زودتر → پیام «بعداً تلاش کنید»)
- **ثبت‌نام در بات:** `/start` → پرسیدن پسورد مشترک (`.env: TELEGRAM_BOT_PASSWORD`) → انتخاب username یونیک → `chat_id` در دیتابیس به کاربر وصل می‌شود؛ کلید `chat_id` از کانفیگ حذف شد؛ تلاش ناموفق پسورد → پیام خطا + لاگ؛ ماشین حالت گفتگو (تایم‌اوت ۱۰ دقیقه در حافظه، بلاک ۵ تلاش ناموفق/۱۰ دقیقه → ۳۰ دقیقه per chat، قواعد username) و دستورات `/start` / `/resend` / `/help` / `/status`: `configuration.md` بخش ۳.۱
- **شمارندهٔ سراسری خطای پسورد (اصلاح ۲۰۲۶-۰۹-۱۸):** جدا از بلاک per-chat، شمارندهٔ سراسری (بین همهٔ chatها) تلاش ناموفق پسورد با آستانه ~۲۰ در ۱۰ دقیقه → **هشدار اپراتور** (chat `TELEGRAM_OPS_CHAT_ID`؛ احتمال بروت‌فورس) + لاگ؛ شمارنده در حافظه
- **409 تلگرام در `getUpdates` (اصلاح ۲۰۲۶-۰۹-۱۸):** گذرا تلقی می‌شود (تزاحم webhook/نمونهٔ دیگر)؛ backoff کوتاه و ادامهٔ polling — نه کرش، نه `dead`
- **مدیریت کاربر با CLI (ADR-0011):** `user list` و `user remove <username>`؛ **حذف کاربر، `pending`های او را هم `dead` می‌کند (G3)** — وگرنه سویپ بعد از حذف همچنان به chat_id او پیام می‌فرستد و حذف بی‌اثر می‌شود؛ ردیف‌های `sent` دست‌نخورده می‌مانند (تاریخچه)
- بارست چند آگهی: هر آگهی یک پیام، قدیمی‌ترین اول، فاصلهٔ ~۱ ثانیه بین پیام‌های تلگرام (~۲ ثانیه ایمیل)؛ ارسال کانال‌ها/گیرنده‌ها مستقل و موازی (خطای یکی مانع دیگری نیست)؛ **429 تلگرام:** انتظار `retry_after` (سقف ۶۰ ثانیه) + یک تلاش مجدد همان پیام — تکرار → طبقهٔ قابل‌احیا با `next_attempt_at` (مصوب ۲۰۲۶-۰۹-۱۷؛ اصلاح ۲۰۲۶-۰۹-۱۸)
- **Bot Gateway (دامنهٔ مینیمال MVP):** long-polling `getUpdates` فقط برای ثبت‌نام (`/start` → پسورد → username)، `/resend YYYY/MM/DD`، `/help` و `/status` (نام کاربری + تعداد pendingها)؛ مدیریت جستجو از بات → backlog؛ `getUpdates` یعنی فقط یک نمونهٔ فعال از سرویس

### ADR-0011: پشته Python + مدیریت جستجو با YAML تنها مرجع (مصوب ۲۰۲۶-۰۹-۱۷)

- **پشته = Python** — دلایل: `sqlite3` در کتابخانهٔ استاندارد (ADR-0001)، کتابخانه‌های بالغ تاریخ شمسی و پردازش متن فارسی، تکرار سریع در فاز کالیبراسیون (تست snapshot، تنظیم قواعد)، هم‌راستا با متن فعلی ADR-0001/0002. گزینه‌های ردشده: Node.js و Go (مزیت تمیز برای این دامنه نداشتند) و .NET 8 (تک‌فایل self-contained و `PersianCalendar` داخلی جذاب بود ولی boilerplate بیشتر و نمونه‌سازی کندتر؛ انتخاب مجدد در صورت تغییر دامنه منتفی نیست)
- **جستجوها فقط در `config.yaml`** تعریف و ویرایش می‌شوند (version-controlled، مرجع یگانه)؛ «افزودن/حذف جستجو» از دامنهٔ CLI حذف شد — CLI فقط `run` / `validate` / `district` / `reset-watermark` / `user`
- **مدیریت کاربر (اصلاح ۲۰۲۶-۰۹-۱۸):** دستورات `user list` (فهرست usernameها + تعداد pending هر کدام) و `user remove <username>` (حذف ردیف `users` + `dead` کردن `pending`های او — ADR-0010/G3)
- **بارگذاری کانفیگ:** در startup و با **SIGHUP** (`systemctl reload top-divar`)؛ YAML نامعتبر در reload → کانفیگ قبلی سر جایش می‌ماند + لاگ ERROR (سرویس نمی‌ایستد)؛ در startup نامعتبر → خطا و بالا نیامدن سرویس
- **جستجوی غایب/غیرفعال:** `enabled: false` یا id غایب در YAML → poll نمی‌شود؛ watermark و `matched_searches` حذف نمی‌شوند (تاریخچهٔ آگهی‌ها مستقل از جستجوست)؛ برگشتِ همان `search_id` → ادامه از watermark قبلی (tombstoneها جلوی تکرار/اسپم آگهی قدیمی را می‌گیرند)؛ watermarkِ بی‌صاحب در دیتابیس → فقط لاگ اطلاعاتی در startup
- **`reset-watermark <search_id>`** (اختیاری): ابزار اپراتور برای baseline عمدی یک جستجو

### ADR-0012: مدل اجرا = asyncio تک‌حلقه با تسک‌های مستقل (مصوب ۲۰۲۶-۰۹-۱۸)

- **یک حلقهٔ رویداد asyncio** در یک پروسه؛ چند **تسک مستقل** روی همان حلقه:

  | تسک | کار |
  |---|---|
  | scheduler | poll جستجوها + صف درخواست‌های دیوار (concurrency = ۱) |
  | bot-gateway | long-polling `getUpdates` + پاسخ دستورات |
  | sweep | ارسال دوره‌ای ردیف‌های `pending` (ADR-0010) |
  | heartbeat | `sd_notify` دوره‌ای برای `WatchdogSec` — **جدا از صف کاری**: قفل‌شدن صف ارسال/پایش نباید watchdog را بخشکند (و برعکس) |

- **قید concurrency=1 با صف، نه قفل کلی:** فقط درخواست‌ها به دیوار (search + جزئیات) از یک صف سریال عبور می‌کنند (AGENTS.md)؛ ارسال نوتیف، پاسخ بات و heartbeat مشمول این صف نیستند و مستقل پیش می‌روند
- heartbeat باید حتی در حالت اشباع صف، به `sd_notify` برسد (وگرنه ری‌استارهای کاذب)؛ بنابراین تسک مستقل است نه گامِ صف
- انتخاب کتابخانه‌های HTTP/async/SQLite → فاز پیاده‌سازی؛ همین ADR فقط شکل اجرا را قفل می‌کند

## ساختار پیشنهادی ماژول‌ها

نقشه منطقی ماژول‌ها (مستقل از زبان؛ نگاشت فیزیکی به پکیج‌ها بعد از تصمیم پشته فناوری):

```
domain/          # مدل‌ها + قراردادها (بدون وابستگی)
core/            # scheduler, detector, normalizer, scorer
infra/
├── divar/       # DivarFetcher
├── storage/     # SqliteRepository, مهاجرت‌ها
└── notify/      # telegram, email (ntfy → backlog)
entry/           # cli, bot-gateway
shared/          # config, logging
```

قاعده وابستگی: `entry → core → domain ← infra`؛ یعنی core فقط دامنه را می‌بیند و آداپتورها فقط دامنه را پیاده می‌کنند.
