# معماری (Architecture)

> این سند پیش‌نویس است؛ تصمیم‌های نهایی اینجا ثبت می‌شوند.

## نمای کلی

```
                ┌──────────────────────────────────────────────┐
                │              CLI / Config                    │
                │  (مدیریت جستجوها، تنظیمات از .env)           │
                └──────────────────────┬───────────────────────┘
                                       │
┌──────────────┐   ┌───────────────┐   │   ┌──────────────┐   ┌─────────────────────┐
│  Scheduler   │──▶│   Fetcher     │──▶│──▶│   Detector   │──▶│     Notifier        │
│ (پایش دوره‌ای)│   │ (دریافت از    │   │   │(جدید/تغییر؟) │   │    (interface)      │
└──────────────┘   │    دیوار)     │   │   └──────┬───────┘   │ Telegram (اصلی)     │
                   └───────────────┘   │          │           │ Ntfy (fallback)     │
                                       │          ▼           │ Email (fallback)    │
                                       │    ┌────────────┐    └─────────────────────┘
                                       │    │  Storage   │
                                       │    │  (SQLite)  │
                                       │    └────────────┘
```

## تقسیم‌بندی معماری

معماری از نوع Ports & Adapters (شش‌ضلعیِ سبک) است: همه وابستگی‌ها به لایه دامنه است و هیچ جزئی به پیاده‌سازی مشخص Fetcher/Storage/Notifier وابسته نیست — تا هر جزء بدون تغییر بقیه قابل تعویض باشد.

### ۱. دامنه و قراردادها (Domain & Ports)

مدل‌های داده و interfaceهای سیستم. مرجع مشترک همه بخش‌ها؛ به هیچ بخش دیگری وابسته نیست.

- موجودیت‌ها: `Search`, `Ad`, `AdEvent`
- قراردادها: `Fetcher`, `AdRepository`, `Notifier`

### ۲. خط لوله اصلی (Core Pipeline)

منطق کسب‌وکار؛ فقط با قراردادهای دامنه کار می‌کند.

- **Scheduler** — حلقه پایش؛ اجرای هر جستجو با بازه خودش، رعایت نرخ درخواست کلی
- **Detector** — مقایسه نتایج تازه با تاریخچه (diff بر اساس `divar_token` و watermark `sort_date`)، تشخیص جدید/bump — semantics کامل: `docs/divar-api.md` بخش ۹ (مرز watermark، poll اول، سقف صفحات، آگهی مشترک بین جستجوها)
- **Normalizer** — تبدیل داده خام کارت search به فیلدهای نرمال‌شده (ارقام فارسی، واحدها، قیمت توافقی) — مرجع نگاشت: `docs/divar-api.md` بخش ۷ و ۸ (فقط فیلدهای کارت search — ADR-0007)
- **Scorer** — اعمال قواعد امتیازدهی کانفیگ (`docs/configuration.md` بخش ۲) روی فیلدهای نرمال‌شده؛ خروجی: امتیاز + شکست آن؛ شرط نوتیف: `score >= min_score`. قواعد نسبی کمیابی (همتای غلتان) در فاز بعد: `docs/deal-scoring.md`، ADR-0008

### ۳. آداپتورها (Adapters)

پیاده‌سازی قراردادها برای دنیای بیرون.

- **DivarFetcher** — دریافت نتایج از دیوار با endpointهای غیررسمی v8 (هدرهای مرورگر واقعی، نرخ محافظه‌کارانه) — تحلیل کامل API: `docs/divar-api.md`، نمونه‌های خام: `docs/fetch-sample.md`
- **SqliteRepository** — تاریخچه آگهی‌ها، جستجوها، تنظیمات (WAL، ایندکس یونیک روی `divar_token`)
- **TelegramNotifier** (کانال اصلی) / **NtfyNotifier** / **EmailNotifier** (fallbackهای SMTP)

### ۴. مقاطع مشترک و ورودی (Cross-cutting & Entry)

- **Config** — بارگذاری `.env` و فایل تنظیمات؛ اعتبارسنجی مقادیر
- **Logging** — لاگ ساختاریافته از وضعیت پایش و خطاها
- **CLI** — نقطه ورود: افزودن/حذف جستجو، اجرای سرویس
- **Bot Gateway** (آینده، backlog) — دریافت دستورات تلگرام و ترجمه به عملیات روی جستجوها

## جریان داده

1. Scheduler سر رسید جستجوی بعدی را می‌گیرد → Fetcher را صدا می‌زند (endpoint `postlist/w/search` با `sort` جدیدترین)
2. Detector نتیجه را با تاریخچه در Storage مقایسه می‌کند (watermark روی `sort_date`)؛ آگهی جدید → Normalizer → Scorer
3. امتیاز `>= min_score` → ذخیره در Storage + ارسال از طریق Notifierها (پیام شامل امتیاز و شکست آن)
4. خطا در هر کانال اطلاع‌رسانی → تلاش برای کانال بعدی + لاگ

## تصمیم‌های ثبت‌شده (ADRها)

### ADR-0001: Storage = SQLite

- تک‌کاربره و حجم کم → بدون سرور، بکاپ = کپی فایل، وابستگی صفر در Python
- `PRAGMA journal_mode=WAL` و `busy_timeout`
- ایندکس یونیک روی `divar_token` (کلید تشخیص تکراری در Detector)
- ذخیره `raw_json` آگهی برای تحلیل‌های آینده (معیار کمیابی نسبی — ADR-0008، `docs/deal-scoring.md`)
- فایل دیتابیس در `data/` و gitignored؛ سیاست purge آگهی‌های قدیمی — نباید کوتاه‌تر از `window_days_max` همتای غلتان باشد (پیشنهادی ≥ ۳۰ روز)
- PostgreSQL فقط در صورت چندکاربره/چندمیزبانی شدن آینده

### ADR-0002: اطلاع‌رسانی چندکاناله

- `Notifier` به‌صورت interface با سه adapter: **Telegram** (اصلی)، **Ntfy**، **Email**
- مزیت تلگرام (Bot API کامل، دستورات تعاملی برای backlog) نگه داشته می‌شود؛ Ntfy/Email fallbackهای سبک و در دسترس
- اگر سرویس روی ماشین داخل ایران باشد، `TelegramNotifier` از `HTTPS_PROXY` استفاده می‌کند

### ADR-0003: سرویس همیشه‌روشن، نه اکستنشن مرورگر

- پایش پیوسته ۲۴/۷، SQLite و SMTP و دستورات بات همگی به یک پروسه همیشه‌روشن نیاز دارند؛ اکستنشن (MV3) این را تضمین نمی‌کند
- استقرار: VPS ارزان خارج از ایران یا سرور خانگی (systemd یا Docker — جزو تصمیم‌های باز)
- اکستنشن حداکثر در آینده به‌عنوان **Fetcher مکمل** (خواندن DOM وقتی کاربر در دیوار است) → ثبت در backlog

### ADR-0004: منبع داده = API غیررسمی وب دیوار (v8) با فیلترهای pass-through

- تنها endpoint فعال: `postlist/w/search` (ترتیب جدیدترین + صفحه‌بندی)؛ `mapview/viewport` رد شد (ADR-0006)؛ جغرافیا با **allowlist محله‌ها** روی `district_persian` (ADR-0006)؛ post detail باز (نیاز به نمونه) — تحلیل کامل: `docs/divar-api.md`
- بدنه درخواستِ فیلترها **عیناً از کانفیگ** ساخته می‌شود (`form_data` بدون ترجمه؛ `docs/configuration.md`) → فیلتر جدید دیوار بدون تغییر کد پشتیبانی می‌شود
- بدون احراز هویت در جستجو (فرض اولیه؛ تست باز)، هدرهای مرورگر واقعی، نسخه `v8` پین
- تشخیص جدید بودن: `divar_token` + watermark `sort_date` (اولین صفحه با ترتیب جدیدترین)
- ریسک API خصوصی/متغیر → تنها از طریق `DivarFetcher` (ایزوله)، تست snapshot روی نمونه‌های `fetch-sample.md`
- گزینه HTML scraping رد شد: JSON ساخت‌یافته، پایدارتر و سبک‌تر از پارس DOM

### ADR-0005: امتیازدهی قاعده‌محور با آستانه نوتیف

- موتور امتیازدهی جدا از فیلترهای جستجو: فیلتر = رد موارد بی‌ربط در سمت دیوار؛ امتیاز = سنجش «خوب بودن» در سمت ما
- قواعد در کانفیگ: `{field, op, value, points}` + قواعد پله‌ای (tiers) + امتیاز منفی (جریمه) — `docs/configuration.md` بخش ۲
- ورودی: فیلدهای نرمال‌شده از داده کارت search (ADR-0007؛ بدون درخواست اضافه در MVP)؛ فیلد غایب → `skip` قاعده؛ تمایز «غایب» و «null صریح (توافقی)»: `configuration.md` بخش ۲
- شرط نوتیف: `score >= min_score`؛ پیام شامل امتیاز و شکست آن (برای کالیبراسیون قواعد)
- قواعد نسبی کمیابی → فاز بعد با معیار **میانهٔ همتای غلتان** (نه دلار، نه میانگین سراسری) — ADR-0008 و `docs/deal-scoring.md`؛ ذخیره `raw_json` (ADR-0001) آن را ممکن می‌کند

### ADR-0006: جغرافیا = allowlist محله‌ها روی `district_persian` (سمت کلاینت)

- مکانیزم جغرافیایی اصلی: کاربر در کانفیگ هر جستجو لیست محله‌های دلخواه (`districts`) را می‌دهد؛ پس‌فیلتر روی `district_persian` پاسخ `search` اعمال می‌شود (`docs/configuration.md` بخش ۱)
- `viewport` (پین‌های نقشه) رد شد: مختصاتش تقریبی است و مصرف‌کننده‌ای ندارد؛ اگر بعداً قاعده امتیاز جغرافیایی خواست شد برمی‌گردد
- `bbox` فقط پیش‌فیلتر اختیاری سرور باقی می‌ماند (pass-through)؛ به‌تنهایی کافی نیست چون مستطیل، محله‌های مجاور را هم می‌گیرد
- تطبیق: **contains** روی متن نرمال‌شده (ي/ك عربی → فارسی، نیم‌فاصله → فاصله) — چون دیوار «نارمک» و «نارمک جنوبی» را جدا برمی‌گرداند
- آگهی خارج از allowlist (یا بدون محله، وقتی `allow_unknown_district: false`) → فقط ثبت seen (بدون امتیازدهی/نوتیف) تا در poll بعدی دوباره پردازش نشود
- مسیر ارتقا بدون شکست کانفیگ: دیوار فیلتر بومی `districts` (ID عددی محله) دارد؛ **فعلاً IDها را کاربر مستقیم در `form_data.districts` می‌گذارد** (فیلتر دقیق سرور) و پس از تهیه جدول نگاشت نام→ID (فاز بعدی)، `districts` نام‌محورِ کانفیگ به این کلید ترجمه می‌شود

### ADR-0007: استخراج فقط از کارت `search` — فیلدهای viewport از نگاشت حذف شد

- جدول نگاشت فیلدها (`divar-api.md` بخش ۷) پیش از این به `subtitle1/2` و `chips` از پاسخ `viewport` ارجاع می‌داد؛ پس از رد viewport (ADR-0006) آن ارجاع‌ها ناسازگار بودند → نگاشت صرفاً بر اسکلت تأییدشده `POST_ROW` سوار شد
- فیلدهای قابل استخراج MVP: `price`، `district`، `city`، `title`، `is_promoted`، `sort_date`، `token`، `image_count`؛ `rebuilt` فقط بافت جستجو (تضمین فیلتر، مقدار ثابت — اطلاعاتی)
- `price_per_square`/`size`/`rooms`/`building_age`/امکانات → تا تأیید نمونه کامل `POST_ROW` یا post detail (فاز بعد) خارج از امتیازدهی MVP (`divar-api.md` بخش ۷.۳)
- semantics «فیلد غایب» در برابر «null صریح (توافقی)» تعریف شد (`configuration.md` بخش ۲) — جریمه توافقی اکنون قابل اجراست
- تشخیص جدید: token یونیک **سراسری** = مرجع dedup (حتی بین جستجوها)؛ watermark فقط سقف صفحه‌بندی (مرز `<`، آیتم‌های هم‌زمان پردازش می‌شوند)؛ poll اول = baseline بدون نوتیف؛ bump فقط با `notify_on_bump` (جزئیات: `divar-api.md` بخش ۹)

### ADR-0008: کمیابی = ارزانی نسبی در همتای غلتان (نه دلار، نه میانگین سراسری)

مرجع تفصیلی: [`docs/deal-scoring.md`](deal-scoring.md)

- مسئله: تورم آستانهٔ ثابت تومانی را می‌سوزاند؛ «آگهی خاص» یعنی نسبت قیمت به شرایط ملک در بازار **همین حالا** کمیاب باشد
- معیار اصلی: **قیمت هر متر** نسبت به **میانه** (و صدک / MAD) آگهی‌های همتا در پنجرهٔ ۱۴–۳۰ روز اخیر — نه میانگین همهٔ آگهی‌ها، نه تبدیل به دلار
- همتا تنگ است (شهر، محله، باند متراژ، باند سن، امکانات در حد داده) با عقب‌نشینی پله‌ای و کف حجم نمونه (`min_cohort_size`؛ پیشنهادی ۳۰)
- سقف بودجهٔ کاربر فیلتر سخت می‌ماند (قواعد مطلق MVP)؛ امتیاز کمیابی جداست و با بازار جلو می‌رود
- دلار حداکثر نمایش اختیاری در پیام است، شرط نوتیف نیست
- پیش‌نیاز: `size` / `price_per_square` از post detail یا کارت کامل (بخش ۷.۳ `divar-api.md`)؛ تا آن زمان MVP فقط قواعد مطلق
- کیفیت ملک با همتاسازی + جریمه‌های قاعده‌محور کنترل می‌شود؛ مدل پیش‌بینی قیمت فاز بعدی اختیاری است

## ساختار پیشنهادی ماژول‌ها

نقشه منطقی ماژول‌ها (مستقل از زبان؛ نگاشت فیزیکی به پکیج‌ها بعد از تصمیم پشته فناوری):

```
domain/          # مدل‌ها + قراردادها (بدون وابستگی)
core/            # scheduler, detector, normalizer, scorer
infra/
├── divar/       # DivarFetcher
├── storage/     # SqliteRepository, مهاجرت‌ها
└── notify/      # telegram, ntfy, email
entry/           # cli (و در آینده: bot gateway)
shared/          # config, logging
```

قاعده وابستگی: `entry → core → domain ← infra`؛ یعنی core فقط دامنه را می‌بیند و آداپتورها فقط دامنه را پیاده می‌کنند.

## ملاحظات فنی

- توکن بات و تنظیمات حساس از متغیرهای محیطی (`.env`)
- لاگ خطاها و وضعیت پایش برای عیب‌یابی
- نرخ درخواست معقول به دیوار؛ بدون درخواست‌های موازی سنگین
- ساختار ماژولار تا جای ممکن برای تعویض Fetcher (در صورت تغییر دیوار)
