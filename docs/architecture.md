# معماری (Architecture)

> این سند پیش‌نویس است؛ تصمیم‌های نهایی اینجا ثبت می‌شوند.

## نمای کلی

```
                ┌──────────────────────────────────────────────┐
                │              CLI / Config                    │
                │  (مدیریت جستجوها، تنظیمات از .env)           │
                └──────────────────────┬───────────────────────┘
                                       │
┌──────────────┐   ┌───────────────┐   │   ┌──────────────┐   ┌─────────────────────┐

│ (پایش دوره‌ای)│   │ (دریافت از    │   │   │(جدید/تغییر؟) │   │    (interface)      │
└──────────────┘   │    دیوار)     │   │   └──────┬───────┘   │ Telegram (اصلی)     │
```

## تقسیم‌بندی معماری

معماری از نوع Ports & Adapters (شش‌ضلعیِ سبک) است: همه وابستگی‌ها به لایه دامنه است و هیچ جزئی به پیاده‌سازی مشخص Fetcher/Storage/Notifier وابسته نیست — تا هر جزء بدون تغییر بقیه قابل تعویض باشد.

### ۱. دامنه و قراردادها (Domain & Ports)

مدل‌های داده و interfaceهای سیستم. مرجع مشترک همه بخش‌ها؛ به هیچ بخش دیگری وابسته نیست.

- موجودیت‌ها: `Search`, `Ad`, `AdEvent`
- قراردادها: `Fetcher`, `AdRepository`, `Notifier`

### ۲. خط لوله اصلی (Core Pipeline)

منطق کسب‌وکار؛ فقط با قراردادهای دامنه کار می‌کند.

- **Scheduler** — حلقه پایش؛ اجرای هر جستجو با بازه خودش، رعایت نرخ درخواست کلی
- **Detector** — مقایسه نتایج تازه با تاریخچه (diff بر اساس `divar_token`)، تشخیص جدید/تغییرکرده، اعمال فیلترهای «خوب بودن»

### ۳. آداپتورها (Adapters)

پیاده‌سازی قراردادها برای دنیای بیرون.

- **DivarFetcher** — دریافت نتایج از دیوار (HTTP با هدرهای مرورگر واقعی و نرخ محافظه‌کارانه)
- **SqliteRepository** — تاریخچه آگهی‌ها، جستجوها، تنظیمات (WAL، ایندکس یونیک روی `divar_token`)
- **TelegramNotifier** (کانال اصلی) / **NtfyNotifier** / **EmailNotifier** (fallbackهای SMTP)

### ۴. مقاطع مشترک و ورودی (Cross-cutting & Entry)

- **Config** — بارگذاری `.env` و فایل تنظیمات؛ اعتبارسنجی مقادیر
- **Logging** — لاگ ساختاریافته از وضعیت پایش و خطاها
- **CLI** — نقطه ورود: افزودن/حذف جستجو، اجرای سرویس
- **Bot Gateway** (آینده، backlog) — دریافت دستورات تلگرام و ترجمه به عملیات روی جستجوها

## جریان داده

1. Scheduler سر رسید جستجوی بعدی را می‌گیرد → Fetcher را صدا می‌زند
2. Detector نتیجه را با تاریخچه در Storage مقایسه می‌کند
3. آگهی جدید/تغییرکرده → ذخیره در Storage + ارسال از طریق Notifierها
4. خطا در هر کانال اطلاع‌رسانی → تلاش برای کانال بعدی + لاگ

## تصمیم‌های ثبت‌شده (ADRها)

### ADR-0001: Storage = SQLite

- تک‌کاربره و حجم کم → بدون سرور، بکاپ = کپی فایل، وابستگی صفر در Python
- `PRAGMA journal_mode=WAL` و `busy_timeout`
- ایندکس یونیک روی `divar_token` (کلید تشخیص تکراری در Detector)
- ذخیره `raw_json` آگهی برای تحلیل‌های آینده (معیار «چند بودن»)
- فایل دیتابیس در `data/` و gitignored؛ سیاست purge آگهی‌های قدیمی
- PostgreSQL فقط در صورت چندکاربره/چندمیزبانی شدن آینده

### ADR-0002: اطلاع‌رسانی چندکاناله

- `Notifier` به‌صورت interface با سه adapter: **Telegram** (اصلی)، **Ntfy**، **Email**
- مزیت تلگرام (Bot API کامل، دستورات تعاملی برای backlog) نگه داشته می‌شود؛ Ntfy/Email fallbackهای سبک و در دسترس
- اگر سرویس روی ماشین داخل ایران باشد، `TelegramNotifier` از `HTTPS_PROXY` استفاده می‌کند

### ADR-0003: سرویس همیشه‌روشن، نه اکستنشن مرورگر

- پایش پیوسته ۲۴/۷، SQLite و SMTP و دستورات بات همگی به یک پروسه همیشه‌روشن نیاز دارند؛ اکستنشن (MV3) این را تضمین نمی‌کند
- استقرار: VPS ارزان خارج از ایران یا سرور خانگی (systemd یا Docker — جزو تصمیم‌های باز)
- اکستنشن حداکثر در آینده به‌عنوان **Fetcher مکمل** (خواندن DOM وقتی کاربر در دیوار است) → ثبت در backlog

## تصمیم‌های باز

- [ ] **پشته فناوری:** گزینه‌ها — Python (پیشنهاد اولیه: کتابخانه‌های غنی برای scraping و تلگرام) / Node.js / Go
- [ ] **روش دریافت داده از دیوار:** API غیررسمی vs. وب‌اسکرپینگ — ملاحظات پایداری و نرخ درخواست
- [ ] **نحوه اجرا:** سرویس systemd / Docker / cron
- [ ] **فرمت پیام تلگرام و متادیتای ارسالی**

## ساختار پیشنهادی ماژول‌ها

نقشه منطقی ماژول‌ها (مستقل از زبان؛ نگاشت فیزیکی به پکیج‌ها بعد از تصمیم پشته فناوری):

```
domain/          # مدل‌ها + قراردادها (بدون وابستگی)
core/            # scheduler, detector
infra/
├── divar/       # DivarFetcher
├── storage/     # SqliteRepository, مهاجرت‌ها
└── notify/      # telegram, ntfy, email
entry/           # cli (و در آینده: bot gateway)
shared/          # config, logging
```

قاعده وابستگی: `entry → core → domain ← infra`؛ یعنی core فقط دامنه را می‌بیند و آداپتورها فقط دامنه را پیاده می‌کنند.

## ملاحظات فنی

- توکن بات و تنظیمات حساس از متغیرهای محیطی (`.env`)
- لاگ خطاها و وضعیت پایش برای عیب‌یابی
- نرخ درخواست معقول به دیوار؛ بدون درخواست‌های موازی سنگین
- ساختار ماژولار تا جای ممکن برای تعویض Fetcher (در صورت تغییر دیوار)
